1. 设计原则
   职责单一：Connector只负责数据采集、格式校验、批量上报，不做任何业务逻辑、AI推理、数据存储，严格对齐Law-002 Observation采集边界
   高可靠：支持断网缓冲、失败重试、降级上报，保证采集数据不丢失，满足核心业务可用性要求
   可扩展：新增采集数据源只需要新增对应的采集实现类，不需要修改现有采集逻辑，符合开闭原则
   对齐规范：所有采集输出严格对齐M2-006 Observation Model的字段要求，无偏差、无冗余
2. 核心职责映射
   职责	对应世界模型	输入	输出	触发条件
   数据采集	M2-006 Observation Model	各类数据源：Prometheus、JMX、Redis Exporter、日志文件、事件源	统一格式的Observation列表	定时采集（默认10秒/次）、事件触发采集
3. 核心实现规则
   3.1 采集流程
   采集前校验：校验采集配置是否合法、数据源是否可达，不可达则跳过本次采集，记录告警日志
   数据采集：按配置的采集频率拉取原始数据，单次采集超时时间默认5秒，超时则本次采集失败
   格式转换：将原始数据转换为IM-002定义的Observation实体格式，必填字段（observation_id、resource_id、observation_type、metric_name、metric_value、created_at）不允许为空
   本地缓冲：上报成功则清空缓冲，上报失败则将数据写入本地缓冲文件，网络恢复后按时间顺序补报
   批量上报：每10秒或者缓冲数据达到1000条时，批量调用IM-006的/api/v1/observations/batch接口上报，禁止单条上报
   失败重试：上报失败最多重试3次，重试间隔依次为1s/2s/4s，3次仍失败则写入本地死信队列，触发人工告警
   3.2 采集器类型
   采集器类型	适用数据源	采集内容
   METRIC_COLLECTOR	Prometheus、JMX、各类Exporter	指标类数据：CPU、内存、QPS、RT等
   LOG_COLLECTOR	应用日志、系统日志	错误日志、异常日志等文本类数据
   EVENT_COLLECTOR	部署系统、配置中心、注册中心	状态变更、配置修改、服务上下线等事件类数据
   3.3 心跳机制
   每30秒向中心服务发送心跳，心跳内容包括：采集器ID、版本号、当前采集状态、已采集数据量、失败次数，连续3次心跳丢失则触发运维告警

4. 约束（Connector绝对禁止的操作）
   禁止存储领域数据：不存储任何Observation、Resource、Evidence等领域数据，只保留临时缓冲文件，缓冲数据最多保留7天自动清理
   禁止调用非采集相关API：仅允许调用IM-006的Observation批量上报接口、心跳接口，禁止调用其他任何业务API
   禁止做业务逻辑处理：不做规则判断、异常检测、AI推理，所有原始数据直接转换格式后上报，由中心服务做后续处理
   禁止直接访问数据库：不直接连接MySQL、ClickHouse、图数据库，所有数据交互通过API网关实现
   禁止硬编码配置：采集频率、数据源地址、上报地址等配置统一从配置中心获取，支持动态更新，不需要重启采集器即可生效
5. 性能要求
   单采集器每秒至少处理10万条指标数据，满足大规模集群采集需求
   内存占用不超过1GB，CPU占用不超过2核，避免影响采集目标的业务性能
   上报接口调用成功率≥99.99%，数据丢失率≤0.001%
   采集器升级支持灰度发布，不影响现有采集任务
6. 验收标准
   ✔ 职责单一，只做采集、格式转换、上报，无越权操作，符合Law-002要求
   ✔ 输出数据完全对齐M2-006 Observation Model，字段无偏差、无冗余
   ✔ 可靠性机制完善，支持断网缓冲、失败重试、降级上报，数据不丢失
   ✔ 可扩展性强，新增数据源只需要新增采集实现类，不需要修改现有代码
   ✔ 性能满足大规模集群采集要求，资源占用符合约束
